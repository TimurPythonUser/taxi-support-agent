Часть 1 задания

Ответы на вопросы

1С чего начнёте разработку и почему?

С контракта данных и набора эталонных диалогов, а не с промпта. Самые дорогие ошибки такого агента — неполное обращение, которое оператору придётся переспрашивать, и выдуманный факт. Обе ловятся, только если заранее определено, что такое «готовое обращение», и есть чем это измерить.

  1. Для каждого сценария — обязательные поля, правила проверки и критерий «готово» (вместе с операторами, по реальным обращениям).
  2. 15–20 эталонных диалогов с ожидаемым итогом — регрессионный тест для любой правки промпта или смены модели.
  3. Детерминированное ядро: состояние, инструменты, заглушки внешних систем, unit-тесты. Здесь живут все гарантии.
  4. LLM-слой и итерации по eval; каналы (API, чат, голос) — последними, это тонкие адаптеры.

2Какие компоненты, модель и библиотеки выберете?

LLM понимает текст и формулирует ответы, а состояние диалога, проверки и бизнес-правила — обычный код вокруг неё.

  • Компоненты: HTTP API → оркестратор (детерминированные проверки до и после модели + цикл «модель ⇄ инструменты») → инструменты → адаптеры к платформе: цены, заказы, обращения, база знаний, хранилище сессий.
  • Модель: DeepSeek Flash без режима рассуждений — надёжные вызовы инструментов, русский и украинский, около $0.002 за диалог. Подключение через OpenAI-совместимый API: провайдер меняется в .env (альтернативы — Claude Haiku 5.5, GPT-5.4 nano). Выбор подтверждает eval-набор, а не прайс.
  • Библиотеки: FastAPI, Pydantic v2, официальный openai SDK, rank-bm25, SQLite в прототипе (в проде Redis + Postgres). Без LangChain/LangGraph: свой цикл на ~250 строк прозрачнее и полностью покрыт тестами.

3Как организуете базу знаний и хранение контекста диалога?

Главная память агента — не история сообщений, а структурированное состояние дела, которое хранит код и каждый раунд подставляет в промпт. Поэтому агент не переспрашивает и не теряет факты.

  • Контекст: состояние дела (сценарий, собранные поля, найденная поездка, расчёт, номер обращения, чего не хватает) + окно последних 12 реплик со всеми вызовами инструментов. Всё сохраняется по session_id: в прототипе SQLite, в проде Redis для активных сессий и Postgres для истории.
  • База знаний: правила сервиса в markdown, нарезанные по разделам, поиск BM25 через инструмент search_knowledge_base. Агент отвечает только по найденному; если ничего не найдено — не импровизирует, а предлагает оператора.
  • В проде: гибридный поиск (BM25 + эмбеддинги) с реранкером, у статей владельцы и версии, регулярный eval по базе. Изменчивые данные (тарифы по городам, акции) — из API платформы, а не из текстов.

4Когда агент должен уточнять информацию или передавать обращение оператору?

Уточнять — когда не хватает обязательного поля или значение неоднозначно; это решает код по состоянию дела. Передавать оператору — по правилам, которые срабатывают без участия модели.

уточнить
  • нет обязательного поля (номер заказа или дата и время, описание вещи, адреса, причина жалобы);
  • значение размыто или не прошло проверку: «вечером» без часа, дата в будущем, неверный номер;
  • найдено несколько поездок или поездку, найденную по дате, нужно подтвердить;
  • сервис цен не распознал адрес.
оператор
  • клиент просит живого человека;
  • угроза безопасности — ДТП, угрозы, насилие, нетрезвый водитель: срочно и с упоминанием 112;
  • нет прогресса 3 реплики подряд или 2 технических сбоя подряд;
  • вопрос о сервисе, на который нет ответа в базе знаний.

Вопросы не о такси — вежливый отказ без оператора. Обращения о забытых вещах и жалобах оператор получает в любом случае — агент их только готовит.

5Как будете проверять качество ответов?

Три уровня: офлайн-тесты гарантий, live-прогоны с симулированным клиентом и проверкой итога кодом, LLM-судья по рубрике. В проде к ним добавляются продуктовые метрики и разметка выборки диалогов.

  • Офлайн: 120 тестов на фейковой модели — проверки полей, защита номера заказа, блокировка неполного обращения, правила передачи оператору. Идут в CI на каждый коммит.
  • Live-eval: 15 сценариев × 3 прогона; клиента играет LLM с персоной и фактами. Код проверяет итог: поля, найденную поездку, цену ровно из сервиса, обращение, приоритет, язык. Судья оценивает переписку по 6 критериям: не выдумывает, не переспрашивает, уточняет при неясности, один вопрос за раз, язык клиента, тон. Результат — 45/45.
  • Прод: доля решённых без оператора, полнота обращений, повторные обращения, CSAT, p95 задержки, стоимость диалога; еженедельная разметка выборки; eval как обязательный шаг CI; новая модель — сначала shadow-режим, потом A/B.

6Как в дальнейшем подключите API платформы и голосовое общение?

Агент отделён от внешних систем интерфейсами, а от канала — HTTP API. Интеграция с платформой — это новые реализации тех же интерфейсов; голос — ещё один канал перед тем же оркестратором.

  • API платформы: OrderRepository — заказы клиента по customer_id из токена приложения (не нужно спрашивать телефон и имя), PriceProvider — тарификация с геокодингом, TicketSink — helpdesk/CRM операторов, SessionStore — Redis и Postgres. Код агента не меняется.
  • Голос: телефония → потоковое распознавание речи → тот же оркестратор с «голосовым» стилем (короткие фразы, номер заказа по цифрам, подтверждение адресов) → потоковый синтез. Главная задача — задержка: сейчас ~4 с на ход, для голоса нужно меньше 1.5 с до первого звука — стриминг в синтез, фразы-заполнители, меньше раундов, быстрая модель.

Библиотеки

Взял

  • FastAPI + Pydantic v2 — API, валидация, модели состояния с сериализацией в JSON.
  • openai SDK — один клиент для любого совместимого провайдера, ретраи и таймауты.
  • rank-bm25 + snowball — поиск по базе знаний без внешних сервисов.
  • SQLite — сессии и обращения в прототипе, за интерфейсом.
  • pytest, ruff, uv, Docker — тесты, линт, воспроизводимая сборка.

Сознательно не взял

  • LangChain / LangGraph — для одного агента с семью инструментами абстракции дороже пользы: сложнее отлаживать и контролировать, что уходит в модель.
  • Векторная БД — четыре страницы правил; эмбеддинги понадобятся на реальной базе знаний.
  • Свободный JSON вместо tools — вызовы инструментов дают типизированные аргументы и естественный цикл «действие → результат».
Знания и контекст

Что видит модель на каждом шаге

Три слоя контекста

  1. Состояние дела — пишется только через инструменты с проверкой и перед каждым вызовом модели рендерится в блок CASE STATE.
  2. Окно истории — последние 12 реплик клиента со всеми вызовами инструментов; режется по границе сообщения клиента, чтобы не оторвать вызов от результата. Старые факты не теряются — они в состоянии.
  3. Хранилище — состояние и полная история по session_id.

Тексты о сроках, которые агент сообщает после создания обращения, тоже приходят из базы знаний вместе с ответом инструмента, а не из промпта.

Уточнение и оператор

Правила в коде, а не в настроении модели

  • Инструмент update_case возвращает missing_fields и подсказку next_step; агент спрашивает по одному пункту.
  • Проверки отклоняют размытые значения с подсказкой, что спросить: «вечером» вместо часа, дата в будущем или старше 90 дней, номер заказа не из 5–10 цифр.
  • Обращение нельзя создать без обязательных полей, без поиска поездки и без подтверждения поездки, найденной по дате и времени.
  • Просьба позвать человека и слова об угрозе безопасности распознаются до модели; безопасность всегда выигрывает — даже при лимитах и сбоях модели передача срочная.
  • После передачи сессия замораживается: клиент получает фиксированный ответ, оператор — обращение с полями дела, причиной и последними репликами. Приоритеты: normal · high для документов, денег, карт и техники · urgent для безопасности.
Как агент не выдумывает

Шесть механизмов, каждый покрыт тестом

  1. Действия берут вход из состояния, а не из аргументов модели. get_trip_price, find_trip, create_operator_ticket не принимают данных: адреса и номер заказа сначала проходят проверку в update_case, а служебные поля модель записать не может.
  2. Защита номера заказа. Номер принимается, только если клиент написал его целиком или его вернул поиск поездки. Модель пыталась «угадать» номер по маршруту — проверка отклонила.
  3. Проверка цен в ответе. Каждая сумма сверяется с ценами из результатов инструментов. Чужая сумма — ответ переписывается; не вышло — безопасный шаблон.
  4. Обращение собирает код. Поля берутся из состояния; модель пишет только короткое резюме.
  5. Правила только из базы знаний. Сроки и порядок рассмотрения — из search_knowledge_base или текста, который возвращает инструмент обращения.
  6. Проверка снаружи. LLM-судья в eval ищет факты, не подтверждённые клиентом или инструментами: 45/45 чисто.

Первый прогон был 40/45, и это полезнее итоговой цифры. Eval нашёл три дефекта, которые unit-тесты не ловили: детали, добавленные после создания обращения, уходили в новое пустое дело (агент при этом говорил «добавил») — появился add_ticket_note; модель копировала найденную поездку обратно в дело, это сбрасывало поиск и зацикливало вызовы — исправлено правило; при исчерпании раундов клиент видел «технический сбой», хотя обращение было создано — теперь финальный ответ без инструментов. Затем код-ревью нашло ещё ряд проблем (безопасность против запроса оператора, ложные срабатывания правил, запись служебных полей) — исправлены и закреплены тестами.

Риски

Что учесть перед продом

Персональные данные

Адреса и детали поездок уходят провайдеру модели. Для DeepSeek (серверы в Китае) — маскирование адресов и телефонов до отправки или модель в нужной юрисдикции / self-hosted. Слой модели меняется через .env.

Prompt injection

Текст клиента не может вызвать привилегированных действий: инструменты не меняют заказы и деньги, вход действий берётся из проверенного состояния, номер заказа защищён, текст клиента в промпте — одной строкой.

Масштабирование

Прототип — один процесс (блокировки сессий в памяти, SQLite). Дальше: несколько stateless-воркеров, Redis для сессий и блокировок, очередь для обращений.

Стоимость

~$0.002 за диалог → около $200 на 100 тыс. диалогов в месяц на модели. В демо стоят лимиты: 40 сообщений на сессию и дневной лимит запросов.

Прототип: Python 3.13, FastAPI, DeepSeek Flash. Запуск, тесты и eval — в README репозитория. Данные о заказах, тарифы и правила в демо вымышлены.
