01

С чего начну разработку и почему

С контракта данных и набора эталонных диалогов, а не с промпта. Самые дорогие ошибки такого агента — неполное обращение, которое оператор будет переспрашивать, и выдуманный факт (цена, срок, «водителя накажут»). Обе ошибки ловятся только если заранее определено, что такое «готовое обращение», и есть способ это измерить.

  1. 1
    Контракт сценариевДля каждого сценария — обязательные поля, правила валидации и критерий готовности. «Забытая вещь» готова, когда есть номер заказа или дата + время, описание вещи и выполнен поиск поездки. Это неделя разговоров с операторами и разбор реальных обращений; в прототипе — agent/state.py.
  2. 2
    Eval-набор до кода15–20 сценариев с ожидаемым итогом: какие поля, какой тикет, какая цена, когда оператор. Он становится регрессионным тестом на каждую правку промпта или смену модели.
  3. 3
    Детерминированное ядроСостояние, инструменты, валидация, заглушки внешних систем — с unit-тестами на фейковой модели. Здесь живут все гарантии; они не зависят от того, какая LLM стоит сверху.
  4. 4
    LLM-слой и итерации по evalПромпт, описания инструментов, подсказки next_step. Первый прогон дал 40/45 и нашёл три реальных бага — после исправлений 45/45 (см. раздел 5).
  5. 5
    Каналы и эксплуатацияHTTP API, веб-чат, CLI, Docker, лимиты стоимости. Дальше — реальные API платформы и голос через те же адаптеры.
02

Компоненты, модель и библиотеки

Гибрид: LLM понимает текст и формулирует ответы, а состояние, валидация и бизнес-правила — обычный код. Свой цикл «модель ↔ инструменты» на официальном SDK без фреймворков: в нём ~250 строк, каждую можно объяснить, и все гарантии проверяются тестами.

Модель

DeepSeek Flash (deepseek-flash) с выключенным reasoning (thinking: disabled). Задача — надёжные вызовы инструментов и короткие ответы на русском и украинском, длинные цепочки рассуждений тут не нужны: без них ответ быстрее и дешевле. Подключение через официальный openai SDK к OpenAI-совместимому API, поэтому смена модели — это строка в .env, без правки кода.

Библиотеки

Взял

  • FastAPI + Pydantic v2 — API, валидация, модели состояния с сериализацией в JSON.
  • openai SDK — единый клиент для любого совместимого провайдера, ретраи и таймауты.
  • rank-bm25 + snowball — поиск по базе знаний без внешних сервисов.
  • SQLite — сессии и тикеты в прототипе, за интерфейсом.
  • pytest, ruff, uv, Docker — тесты, линт, воспроизводимая сборка.

Сознательно не взял

  • LangChain / LangGraph — для одного агента с шестью инструментами абстракции дороже пользы: сложнее отлаживать и контролировать, что уходит в модель.
  • Векторная БД — четыре страницы правил; эмбеддинги понадобятся на реальной базе знаний (раздел 3).
  • Свободный JSON-вывод вместо tools — tool calling даёт типизированные аргументы и естественный цикл «действие → результат».
03

База знаний и контекст диалога

Контекст диалога — это не только история сообщений. Главная память агента — структурированное состояние дела, которое код хранит и каждый раунд подставляет в системный промпт. Поэтому агент не переспрашивает и не теряет факты, даже когда старые реплики выпадают из окна.

Три слоя контекста

  1. Состояние дела — сценарий, слоты, найденная поездка, расчёт цены, номер тикета, что ещё не хватает. Пишется только через инструменты с валидацией; рендерится в блок CASE STATE перед каждым вызовом модели.
  2. Окно истории — последние 12 реплик клиента со всеми вызовами инструментов. Режется по границе сообщения клиента, чтобы не оторвать вызов инструмента от результата.
  3. Хранилище — состояние и полная история по session_id в SQLite; в проде горячие сессии в Redis с TTL, архив и тикеты в Postgres.

База знаний

Правила сервиса (сроки поиска вещей, тарифы, ожидание, отмена, порядок жалоб) — markdown-файлы, нарезанные по разделам ##, поиск BM25 с русским стеммингом и усилением заголовка раздела. Агент обращается к ней через search_knowledge_base и отвечает только по найденному; если ничего не найдено, инструмент прямо говорит «не отвечай из общих знаний». Тексты о сроках, которые агент сообщает после создания тикета, тоже приходят из базы, а не из промпта.

На реальном объёме (сотни статей, внутренние регламенты операторов):

  • гибридный поиск BM25 + эмбеддинги и реранкер; contextual retrieval — к каждому чанку дописывается контекст документа;
  • у каждой статьи владелец и дата ревизии, версии в git; eval-набор вопросов к базе (Recall@k, faithfulness) гоняется при каждом изменении;
  • отдельно — «динамические» знания (тарифы по городам, акции) не в текстах, а через API платформы, чтобы не устаревали.
04

Когда уточнять, а когда звать оператора

Уточнять — когда не хватает обязательного поля или значение неоднозначно; это решает код по состоянию дела, а не модель «по ощущению». Передавать оператору — по детерминированным триггерам, которые срабатывают без участия модели, плюс когда вопрос о сервисе не покрыт базой знаний.

уточнить

  • Обязательное поле пустое — инструмент возвращает missing_fields и next_step; агент спрашивает по одному пункту.
  • Значение не проходит валидацию: «вечером» вместо часа, дата в будущем, номер заказа не из 5–10 цифр — валидатор отклоняет с подсказкой, что спросить.
  • Найдено несколько поездок — агент просит выбрать по маршруту или времени, не угадывает.
  • Поездка найдена по дате и времени — агент подтверждает её у клиента перед тикетом.
  • Адрес не распознан сервисом расчёта — просит улицу и дом.

оператор

  • Клиент просит человека — регулярное выражение, модель даже не вызывается.
  • Безопасность (ДТП, угрозы, насилие, домогательства, нетрезвый водитель) — срочный приоритет, упоминание 112; если модель не передала сама, код передаёт принудительно.
  • Нет прогресса 3 реплики подряд — недостающие поля не заполняются.
  • Два сбоя подряд — модели или внешнего API.
  • Вопрос о сервисе вне базы знаний — решает модель через handoff_to_operator. Вопросы не о такси (рестораны, погода) — вежливый отказ без оператора.

После передачи сессия замораживается: на следующие сообщения клиент получает фиксированный ответ, а оператор — тикет с полями дела, причиной и последними репликами. Приоритеты: normal · high для документов, денег, карт и техники · urgent для безопасности.

Как агент не выдумывает

Промпт просит не выдумывать, но держат это пять механизмов в коде — каждый покрыт тестом.

  1. Действия берут вход из состояния, а не из аргументов модели. get_trip_price, find_trip, create_operator_ticket без аргументов данных: адреса и номер заказа сначала должны пройти через update_case.
  2. Grounding номера заказа. Номер принимается, только если эти цифры есть в сообщениях клиента или вернулись из find_trip. Модель пыталась «угадать» номер по маршруту — проверка отклонила.
  3. Output-guard цен. Каждая сумма в ответе сверяется с числами из результатов инструментов. Чужая сумма — ответ переписывается; не вышло — безопасный шаблон.
  4. Тикет собирает код. Структурированные поля обращения берутся из состояния; модель пишет только короткое резюме. Без обязательных полей тикет не создаётся.
  5. Политики только из базы знаний. Сроки, порядок рассмотрения, условия — из search_knowledge_base или текста политики, который возвращает инструмент тикета.
  6. Проверяется снаружи. LLM-судья в eval ищет любые факты, не подтверждённые клиентом или инструментами: 45/45 чисто.
05

Как проверять качество ответов

Три уровня: офлайн-тесты гарантий на фейковой модели, live-eval с симулированным клиентом и проверкой итогового состояния, LLM-судья по рубрике. В проде к ним добавляются продуктовые метрики и разметка выборки диалогов.

1. Офлайн — 101 тест, ~4 с

Фейковая модель проигрывает сценарий вызовов. Проверяется то, что не должно зависеть от модели: валидация, grounding, блокировка тикета, guardrails, передача оператору, окно истории, API. Идут в CI на каждый коммит.

2. Live-eval — 15 сценариев × 3

Клиента играет LLM с заданной персоной и фактами («номер не помню, было около восьми»). Итог проверяется кодом: сценарий, поля, номер найденной поездки, цена в ответе ровно из сервиса, тикет, приоритет, язык. Затем судья оценивает переписку по 6 критериям.

Судья: «не выдумывает», «не переспрашивает», «уточняет при неясности», «один вопрос за раз», «язык клиента», «тон» — по 45/45. Средняя стоимость диалога вместе с вызовами инструментов — $0.002.

Первый прогон был 40/45, и это полезнее итоговой цифры. Eval нашёл три реальных дефекта, которые unit-тесты не ловили: детали, добавленные после создания тикета, уходили в новое пустое дело (агент при этом говорил клиенту «добавил») — появился add_ticket_note; модель копировала найденную поездку обратно в дело, это сбрасывало поиск и зацикливало вызовы — поправлено правило инвалидации; при исчерпании раундов клиент видел «технический сбой», хотя тикет был создан — теперь финальный ответ без инструментов. Каждый случай закреплён unit-тестом.

В проде

  • Продуктовые метрики: доля решённых без оператора, доля передач и их причины, полнота тикета (оператору не пришлось переспрашивать), повторные обращения в течение 24 ч, CSAT после диалога, p95 задержки, стоимость диалога.
  • Аудит: еженедельная выборка диалогов на разметку; каждый тикет, который оператор исправил, превращается в новый eval-сценарий.
  • Выкатка: eval как обязательный gate в CI для промптов и смены модели; новая модель — сначала shadow-режим на реальном трафике, потом A/B на доле сессий.
  • Наблюдаемость: каждый ход уже пишет структурированные события (инструмент, аргументы, результат, мс) — их в OpenTelemetry-трейсы с session_id.
06

Подключение API платформы и голосового общения

Агент изолирован от внешнего мира интерфейсами, а от канала — HTTP API. Поэтому интеграция с платформой — это реализации OrderRepository, PriceProvider и TicketSink, а голос — ещё один канал перед тем же оркестратором со своим профилем ответов.

API платформы

ИнтерфейсСейчасВ проде

PriceProviderдетерминированная формулаAPI тарификации с геокодингом; ошибки «адрес не найден» и «сервис недоступен» уже различаются агентом
TicketSinkSQLitehelpdesk / CRM (очередь операторов) через API или вебхук, идемпотентный ключ на сессию
SessionStoreSQLiteRedis (горячие сессии, блокировки) + Postgres (история), несколько воркеров без состояния

Каналы (чат в приложении, Telegram, WhatsApp) — тонкие адаптеры над POST /sessions/{id}/messages; операторская консоль получает тикеты и подхватывает замороженную сессию.

Голос

Главная проблема голоса — задержка. Сейчас ход с 1–2 вызовами инструментов занимает ~4 с (медиана на живой модели), для голоса нужно <1.5 с до первого звука. План:

  • стриминг ответа модели сразу в TTS и короткая фраза-заполнитель («сейчас посмотрю поездку»), пока работают инструменты;
  • меньше раундов: update_case и действие в одном ответе модели (параллельные tool calls), подсказки next_step уже к этому подталкивают;
  • самая быстрая модель с хорошим tool use по eval; альтернатива — realtime speech-to-speech модель с теми же инструментами;
  • голосовые особенности: номер заказа диктуется и переспрашивается по цифрам, адрес подтверждается, можно перебить агента (barge-in), DTMF как запасной ввод.

Риски и что дальше

Персональные данные

Адреса и детали поездок уходят провайдеру модели. Для DeepSeek (серверы в Китае) — маскирование адресов и телефонов до отправки или модель в нужной юрисдикции / self-hosted. Слой модели заменяется через .env.

Prompt injection

Клиентский текст не может вызвать привилегированных действий: инструменты не меняют заказы и деньги, вход действий берётся из провалидированного состояния, номер заказа проходит grounding. В проде — ещё и фильтр по customer_id.

Масштабирование

Прототип — один процесс (блокировки сессий в памяти, SQLite). Дальше: несколько stateless-воркеров, Redis для сессий и блокировок, очередь для тикетов.

Стоимость

~$0.002 за диалог → около $200 на 100 тыс. диалогов в месяц на модели. В демо стоят лимиты: 40 сообщений на сессию и дневной лимит запросов.

Прототип: Python 3.13, FastAPI, DeepSeek Flash. Запуск, тесты и eval — в README репозитория. Данные о заказах, тарифы и правила в демо вымышлены.
