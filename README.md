# Агент поддержки такси

Прототип AI-агента поддержки для службы такси. Три сценария:

- **забытая вещь** — уточнить номер заказа или дату и время поездки, описание вещи, найти поездку, оформить обращение оператору;
- **стоимость поездки** — уточнить адреса, получить цену из сервиса расчёта (заглушка), сообщить клиенту;
- **жалоба на водителя** — найти поездку по номеру или по дате, времени и маршруту, выяснить причину, оформить обращение.

Агент держит контекст, не переспрашивает уже известное и не выдумывает факты: цены, данные поездок и правила приходят только из инструментов, а обращение собирает код из провалидированного состояния.

- **Демо:** https://taxi.167-233-175-131.nip.io (логин и пароль — у автора)
- **Описание подхода** (ответы на вопросы ТЗ, схемы, результаты eval): [`docs/approach.html`](docs/approach.html). В демо открывается по ссылке «Подход» (`/approach`).

## Быстрый старт

Нужны Python 3.13 и [uv](https://docs.astral.sh/uv/).

```bash
uv sync
cp .env.example .env        # впишите LLM_API_KEY (или экспортируйте DEEPSEEK_API_KEY)
uv run taxi-agent serve     # http://127.0.0.1:8000 — веб-чат, /docs — Swagger
```

Чат в терминале:

```bash
uv run taxi-agent chat --debug                              # агент в процессе, видно вызовы инструментов
uv run taxi-agent chat --url https://… --user … --password …  # против развёрнутого API
```

Docker:

```bash
docker compose up --build   # http://127.0.0.1:8000, данные в volume taxi-data
```

### Деплой

Демо работает на VPS: контейнер из `docker-compose.yml` без публичных портов, перед ним Caddy в той же docker-сети `taxi-net`. Caddy даёт HTTPS, Basic Auth и строгие заголовки безопасности. Пример блока лежит в [`deploy/Caddyfile.example`](deploy/Caddyfile.example).

```bash
git clone <repo> ~/taxi-agent && cd ~/taxi-agent
printf 'LLM_API_KEY=%s\n' "$KEY" > .env && chmod 600 .env
docker compose up -d --build
docker network connect taxi-net caddy   # затем блок в Caddyfile и `caddy reload`
```

## Модель

По умолчанию DeepSeek Flash (`deepseek-flash`) без reasoning. Клиент — официальный `openai` SDK, поэтому подходит любой OpenAI-совместимый провайдер. Модель меняется в `.env`, код не трогается:

```env
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-5.4-nano
LLM_API_KEY=sk-...
LLM_EXTRA_BODY={}
# reasoning-модели OpenAI: другое имя лимита и без temperature
# LLM_MAX_TOKENS_PARAM=max_completion_tokens
# LLM_TEMPERATURE=none
```

## HTTP API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/sessions` | новая сессия |
| `POST` | `/api/sessions/{id}/messages` | `{"text": "..."}` → ответ агента, состояние дела, трасса вызовов, тикеты, расход токенов |
| `GET` | `/api/sessions/{id}` | история и текущее состояние |
| `GET` | `/api/sessions/{id}/tickets` | обращения, созданные в сессии |
| `GET` | `/api/demo/trips` | тестовые поездки из заглушки заказов |
| `GET` | `/healthz` | проверка живости |

| 731870 | вчера 20:10 | Пейзажная аллея → ул. Лесковая, 9 |

## Проверка качества

```bash
uv run pytest                              # 147 офлайн-тестов, фейковая модель, ~6 с
uv run pytest qa                           # 68 QA-проб на слабые места (qa/PLAN.md), тоже офлайн
uv run python -m evals.run --runs 3        # live-eval: 15 сценариев, симулятор клиента + LLM-судья
uv run python -m qa.live.run --runs 2      # 14 враждебных live-сценариев (ложные тревоги, инъекции, бренды…)
```

Судью eval можно запустить на другой модели, чтобы агент не оценивал сам себя:
`EVAL_JUDGE_MODEL=<модель> EVAL_JUDGE_API_KEY=<ключ> uv run python -m evals.run` (по умолчанию — OpenAI API).

Последний отчёт — [`evals/report.md`](evals/report.md): 45/45 прогонов, средняя стоимость диалога $0.002.

## Как устроено

```
src/taxi_agent/
  agent/state.py          состояние дела: сценарии, слоты, что обязательно и чего не хватает
  agent/tools.py          инструменты для модели: валидация, grounding номера заказа, тикеты
  agent/guardrails.py     детерминированные проверки: оператор, безопасность, язык, выдуманные цены
  agent/prompts.py        системный промпт (EN) и блок состояния, который видит модель
  agent/orchestrator.py   цикл модель ⇄ инструменты, проверки до и после модели
  integrations/           PriceProvider, OrderRepository, TicketSink — интерфейсы и заглушки
  kb/ + knowledge_base/   правила сервиса в markdown и BM25-поиск
  storage/sqlite.py       сессии, тикеты, дневной лимит запросов
  api/app.py, web/        FastAPI и демо-интерфейс
  cli.py                  taxi-agent chat / serve
evals/                    live-сценарии, симулятор клиента, судья, отчёт
tests/                    офлайн-тесты
qa/                       QA-пробы на слабые места и враждебные live-сценарии (qa/PLAN.md)
```

Ключевые решения:

- **Состоянием владеет код.** Модель пишет в дело только через `update_case`. Действия (`find_trip`, `get_trip_price`, `create_operator_ticket`) берут вход из состояния, а не из своих аргументов.
- **Номер заказа проходит grounding.** Он принимается, только если клиент его написал или его вернул поиск поездки.
- **Output-guard цен.** Сумма в ответе, которой нет в результатах инструментов, заставляет переписать ответ.
- **Оператор по правилам.** Просьба позвать человека, угроза безопасности, отсутствие прогресса и повторные сбои передают диалог оператору без участия модели.
- **Модель видит состояние каждый раунд.** Блок `CASE STATE` перерисовывается после каждого вызова инструмента.

Ограничения прототипа: один процесс (блокировки сессий в памяти, SQLite); данные заказов, тарифы и правила вымышлены.
